# 后续排查流程

1. 先确认具体平台、客户端、配置标签、实际模式、系统代理/TUN 开关、住宅与机场前置选择；每条证据标注时间。不要把 10-12 日志当作今天的请求。
2. 保存当前可用版本，围绕一个明确症状选一个对照。分别看首页、认证、接口、视频、直播长连接和安装包。
3. 用用户正常浏览器或客户端复现一次；获取目标域名/IP、进程、TCP/UDP、命中规则、出站链及错误。信息不足时优先索取这些字段，不要求无意义地重复导出相同 info 日志。
4. 先静态检查规则顺序、是否命中更宽泛规则、SOCKS5 是否支持 UDP、是否有相邻拒绝保护、域名 DNS 策略及 hosts 的适用范围。
5. 每次只改有证据支持的部分。区别路由改变与 DNS 调度；区别浏览器启动参数与配置规则；Windows 与安卓分开对照。
6. 先运行本仓库离线检查。若未来已明确准备好匹配版本 Mihomo，可只用 -t 离线校验；不要自动下载或启动核心、不要新建 TUN。
7. 给用户原正常使用路径的复测步骤和回退文件。用户本地结果到达前标注“离线通过/待实测”。

云端环境不能直接读取用户电脑的监听、日志、浏览器、TUN 或安卓 VPN。localhost 指向云端自身，不是用户电脑；不要对云端 7890 发请求来验证用户住宅代理。

不要重复：错误端口测试、把 Cloudflare challenge 403 当断网、仅凭出口查询推断全部请求、把 DIRECT 等同速度正常、依据单个检测分数换节点、把固定 hosts 推广到整个平台、以全局模式判断规则失效。

对于新问题，优先保留浏览器资料与安全设置；不要默认清站点数据、禁用证书验证、改整个 DNS、批量补域名或再次同时运行多个测试核心。

10-25 补充：模式对照必须保留“全局”“规则”标签。显式 7890 不意味着请求固定出住宅，规则仍可 DIRECT；先确认目标是细分业务分流还是 Chrome 全站统一出口，再决定是否调整覆盖范围。避免用补检测站的方式替代真实保护范围验证。
