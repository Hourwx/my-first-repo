# 实测结论、假设与已纠正的误判

## ChatGPT：两个症状分开

| 证据 | 能支持的判断 | 不能据此声称 |
| --- | --- | --- |
| chatgpt.com 连接重置；auth.openai.com 地区拒绝 | 存在两个不同症状 | 两者一定由同一原因造成 |
| 配置写 7893，FlClash 实际监听 127.0.0.1:7890 | 最初指定 7893 的失败是端口用错 | 住宅节点故障 |
| curl 与原 Chrome 的 IPinfo 出口相同 | 当次 IPinfo 请求出口一致 | 全部认证请求路径一致、IP 一定是真住宅 |
| curl 返回 403 且 cf-mitigated: challenge | 已收到 Cloudflare 挑战 | 网络断开或地区封禁 |
| Chrome 禁用 QUIC 后首页恢复 | QUIC/UDP 路径兼容性与首页故障有关 | UDP 是全部登录问题的唯一根因 |
| auth.openai.com 命中 openai.com 代理规则 | 本地认证请求已被接管并选住宅链 | 服务端最终出口及地区判断一定正确 |
| 清站点数据后仍失败 | 此操作未解决当次问题 | 应继续反复清空浏览器 |
| 原资料不变，完全退出后显式 7890 代理启动并重新认证成功 | 强烈支持启动方式/连接路径差异 | 已唯一定位 TUN、扩展、嗅探或系统代理 |

## 抖音：业务、媒体、DNS 与协议分开

- Windows 报过 -7 ERR_TIMED_OUT、-100 ERR_CONNECTION_CLOSED；错误文字本身不能定位哪段链路关闭。
- 日志中的 DomainSuffix(douyin.com) → 出口选择 → 住宅，只证明当次匹配与选择，不证明 TLS/HTTP 成功。
- Chrome 能开、客户端不能开，不能立即认定是客户端自身故障；旧对照发现过 Chrome 从物理网卡 IPv6 绕行的情况。
- 10-12 截图中 douyin.exe 的 v26-webf.douyinvod.com 多次命中 DIRECT，证明这些媒体请求分流生效；不能将慢速概括为所有视频都走住宅。
- www 单域名 hosts 对照后首页恢复；imapi 单域名 hosts 对照后用户确认变快。保留这一有效基线，但不扩大到未经验证的域名。
- 原客户端日志中部分首页 HTTP 200、视频 HTTP 206，与 live/imapi 等残留连接关闭同时存在；一次页面成功不能代表所有功能恢复。

## 升级与配置变动分开

10-21 所选配置的头部明确记载删除两条 hosts，而且保留了 10-14 的其他规则调整。没有证据证明是更新程序自动删掉 hosts。已恢复两条 hosts 并保留后续规则，不能整份回滚到 10-12。

磁盘 config.yaml、偏好与 UI 曾不同步；使用带时间的 UI 和当次请求记录确认模式。10-21 用户截图是规则，现场后来看到全局，两个时段不能混写。

## UDP 与 WebRTC

早期日志存在 Chrome 的 Google 账号 UDP 请求跳过不支持 UDP 的住宅选择、最终 DIRECT 的情况；这是独立于抖音 TCP 关闭的缺口。曾按具体内核实现增加相邻 UDP 拒绝保护，安卓又加入 STUN 3478 / 19302 保护。

保护依赖流量进入内核和规则能够匹配，不能宣称一组端口规则阻止了所有 WebRTC 或 IPv6 泄漏。某网站检测通过也不证明所有客户端路径相同。

## 住宅与质量评分

旧住宅节点与后来纽约节点曾被第三方网站标为同一 ASN 的 ISP/住宅类别，评分网站之间存在差异。运营商 ASN、标记、IPinfo privacy=false、没有黑名单记录或“98 分”均不能证明物理家庭宽带、永久可用或 AI 服务不会风控。

纽约节点后来过期。早期 Windows 第三方检测曾显示 IPv4 美国而所谓 Claude 出口为中国 IPv6；安卓对照则显示目标出口一致。不能把一次检测站的名称当作服务端直接提供的出口证明，也不能把差异完全归因于买到的新旧 IP 质量。

## 被撤回的早期方案

宝可梦“住宅抖音连接修正版”曾使用 DNS normal 等调整，隔离核心测试通过后，用户实际导入却全部 Timeout，已撤回并恢复 fake-ip 基准。隔离测试不能取代实际 FlClash/TUN 验证。该版仅归档，不能因标题含“修正版”就推荐使用。
